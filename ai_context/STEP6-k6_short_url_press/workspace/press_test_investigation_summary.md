# 壓測效能排查總結：從 725 req/s 到 8096 req/s 的除錯過程

## 背景

在對短網址轉址服務（`GET /{shortKey}`）進行 k6 高併發壓測時，發現同一支測試腳本、同樣的負載曲線（Warm-up 30s → Ramp-up 1m → Sustain 200 VU 2m → Ramp-down 30s），
在不同的測試輪次之間，效能數字出現大幅度、且方向不合理的波動，因而展開排查。

---

## 五輪測試完整數據

| 輪次 | 環境狀態 | 吞吐量 (req/s) | avg 延遲 | P50 | P95 | P99 | max |
|---|---|---|---|---|---|---|---|
| #1 | 全新乾淨環境（首次測試） | 2,561.26 | 54.32ms | 36.50ms | 165.06ms | (未測) | 708.53ms |
| #2 | 沿用 #1 的 MySQL/Redis 舊資料，未清空、未重啟 | 975.40 | 142.74ms | 157.2ms | 344.99ms | 509.58ms | 1.38s |
| #3 | 清空 MySQL (`TRUNCATE`) + Redis (`FLUSHALL`)，**但 Spring Boot process 未重啟** | 725.27 | 191.99ms | 209.49ms | 449.53ms | 660.33ms | 1.76s |
| #4 | 清空 MySQL + Redis，**重啟 Spring Boot process**，日誌等級維持 `DEBUG` | 8,096.80 | 17.14ms | 18.20ms | 46.08ms | 68.96ms | 220.98ms |
| #5 | 清空 MySQL + Redis，**重啟 Spring Boot process**，日誌等級改為 `INFO` | 8,219.19 | 16.88ms | 18.29ms | 45.39ms | 67.86ms | 213.41ms |

（全部五輪的正確性指標：`status 302` 通過率 100%、`Location` header 正確率 100%、`http_req_failed` 錯誤率 0.00%，全程沒有任何一輪出現轉址錯誤或資料污染。）

---

## 排查過程（假設 → 驗證 → 推翻 → 定案）

### 第一個假設：MySQL 資料量累積拖慢查詢（#1 → #2）

觀察到 #2（帶著 #1 累積下來的舊資料再測一次）比 #1 慢了 2.63 倍，直覺懷疑是 MySQL 裡累積的資料量（尤其 access log 表）拖慢了查詢效能。

**驗證動作**：清空 MySQL `short_urls` 表與 access log 表、`FLUSHALL` Redis，重新測試（#3）。

**結果推翻假設**：#3 不但沒有變快，反而比 #2 更慢（725 vs 975 req/s）。證明資料量本身不是主因，或至少不是唯一原因——因為理應「清空後應該至少回到接近 #1 的水準」，但沒有發生。

### 第二個假設：process 長時間運行累積狀態（連線池/TIME_WAIT/GC）

由於 #1→#2→#3 期間，Spring Boot process 從未重啟，只是資料表被清空，懷疑問題出在**process 本身的狀態**，而非資料庫內容：
- TCP TIME_WAIT 連線堆積（累計三輪已超過百萬次 HTTP 請求）
- JVM Heap/GC 壓力持續累積
- 連線池（MySQL/Redis connection pool）狀態未重置

**驗證動作**：清空 MySQL + Redis，並且**徹底重啟 Spring Boot process**，重新測試（#4）。

**結果**：吞吐量從 725 req/s 直接跳升到 8,096.80 req/s，提升超過 **11 倍**，P95 延遲從 449.53ms 降到 46.08ms。

### 第三個變因：順手把日誌等級從 DEBUG 改成 INFO,需要拆解驗證

#4 重啟時，同時把日誌等級從 `DEBUG` 改成了 `INFO`,與「process 重啟」這個變因混在一起，無法確定效能提升的真正原因。

**驗證動作（控制變因法）**：固定使用乾淨環境 + 重啟 process，**刻意把日誌等級改回 DEBUG**，其餘條件不變，重新測試（#4 本身即為此對照組，#5 為 INFO 版本）。

**結果**：#4（DEBUG，8,096.80 req/s）與 #5（INFO，8,219.19 req/s）幾乎沒有差異（差距 < 2%，在測試雜訊範圍內）。

**結論**：日誌等級對本次效能提升**沒有實質貢獻**，真正的關鍵變因是 **Spring Boot process 重啟**本身，很可能與 JVM 長時間運行累積的資源狀態（連線池、TIME_WAIT port、GC 壓力）有關。

---

## 最終結論

1. **正確性全程無虞**：五輪測試、累計超過 500 萬次請求，302 跳轉與 Location Header 正確率始終維持 100%，錯誤率 0.00%，系統的核心轉址邏輯在高併發下沒有出現資料錯亂或競爭問題。
2. **效能瓶頸的真因是測試環境未重置，不是程式邏輯或資料庫資料量問題**：長時間運行的 process 會累積連線池/GC/TCP 連線等狀態，若壓測前只清空資料庫內容而不重啟服務，會得到失真、逐輪劣化的數據。
3. **日誌等級（DEBUG vs INFO）在本次測試中不是效能瓶頸**，先前推測的「DEBUG 日誌造成磁碟 I/O 阻塞」經對照測試證實不成立，應予以修正。
4. **方法論教訓**：壓測必須清楚定義並固定「測試前的初始狀態」，每次測試前應同時做到「清空資料庫/快取」+「重啟服務 process」，兩者缺一不可，否則測試數據之間不具可比性，容易導致誤判根因。

---

## 待補充（後續可選的深入驗證）

以下項目本次未實際測量，若要完全鎖死根因，可在下次測試時一併觀察：
- 長時間不重啟連續多輪測試時，`ss -ant | grep TIME_WAIT | wc -l` 的變化趨勢
- `jstat -gcutil <pid> 1000` 觀察 Full GC 次數與耗時是否隨測試輪次增加
- MySQL / Redis connection pool 的即時使用率監控
