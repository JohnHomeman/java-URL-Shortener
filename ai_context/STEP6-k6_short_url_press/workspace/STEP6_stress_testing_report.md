# STEP6：高併發壓力測試總結報告

短網址轉發服務（URL Shortener）— k6 壓力測試成果

---

## 1. 測試目標與範圍

本階段針對 `GET /{shortKey}` 轉址核心路徑，在高併發情境下驗證三件事：

1. **正確性**：高併發下短碼轉址是否每一筆都對應到正確的原始網址，沒有資料錯亂或競爭問題
2. **效能**：系統在 200 VU 併發下的延遲分佈（P95/P99）與錯誤率是否符合預期標準
3. **韌性**：在極端情境（單一熱門連結被大量集中點擊）下，快取層是否依然維持正確性與穩定性

測試工具：[k6](https://k6.io/)，測試腳本：`short_url_press.js`（全域隨機壓測）、`short_url_press_hotkey.js`（熱 Key 專項壓測）
測試環境：本機（筆電）同時運行 Spring Boot + MySQL + Redis + k6

---

## 2. 測試一：全域隨機轉址高併發測試

### 2.1 負載設計

四階段負載曲線：Warm-up（30s → 10 VU）→ Ramp-up（1m → 200 VU）→ Sustain（2m，維持 200 VU）→ Ramp-down（30s → 0 VU），共 4 分鐘。每輪迭代從預先建立的短碼清單中**隨機**挑選一組發送 `GET`，模擬多組連結分散被點擊的真實情境。

### 2.2 最終有效結果（乾淨環境 + process 重啟後）

| 指標 | 門檻標準 | 實測結果 | 判定 |
|---|---|---|---|
| P95 延遲 | < 200ms | **45.39 ms** | ✅ PASS |
| P99 延遲 | < 500ms | **67.86 ms** | ✅ PASS |
| 錯誤率 | < 1% | **0.00%** | ✅ PASS |
| 轉址正確率（Location Header 比對） | = 100% | **100.00%**（1,975,057 / 1,975,057） | ✅ PASS |
| 吞吐量 | — | **8,219.19 req/s** | 參考值 |

4 分鐘內累積 **197 萬次**轉址請求，302 狀態碼與 `Location` header 比對全數正確，無任何一筆跳轉錯誤，錯誤率為零。

### 2.3 重要發現：測試環境的初始狀態會嚴重影響數據可信度

在達到上述最終結果之前，同一支腳本、同樣的負載曲線，實際跑了五輪，數字出現大幅波動：

| 輪次 | 環境狀態 | 吞吐量 (req/s) | P95 | P99 |
|---|---|---|---|---|
| #1 | 全新乾淨環境（首次測試） | 2,561 | 165.06ms | 未測 |
| #2 | 沿用 #1 的 MySQL/Redis 舊資料，未清空、未重啟 | 975 | 344.99ms | 509.58ms |
| #3 | 清空 MySQL + Redis，但 **Spring Boot process 未重啟** | 725 | 449.53ms | 660.33ms |
| #4 | 清空 MySQL + Redis，**重啟 process**，日誌維持 DEBUG | 8,096 | 46.08ms | 68.96ms |
| #5 | 清空 MySQL + Redis，**重啟 process**，日誌改為 INFO | 8,219 | 45.39ms | 67.86ms |

**排查結論**：
- 一開始懷疑是 MySQL 資料量累積拖慢查詢（#1→#2），但清空資料表後（#3）數字不升反降，推翻此假設
- 進一步發現，真正的關鍵變因是 **Spring Boot process 是否重啟**，而非資料庫內容或日誌等級——process 長時間運行會累積連線池狀態、TCP TIME_WAIT 連線、GC 壓力等，這些都不是單純清空資料庫能重置的
- 額外用控制變因法驗證：固定乾淨環境 + 重啟 process，僅切換日誌等級（DEBUG vs INFO），兩者結果幾乎無差異（8,096 vs 8,219 req/s，差距 < 2%），排除日誌 I/O 是效能瓶頸的假設

**方法論教訓**：壓測前必須同時做到「清空資料庫/快取」+「重啟服務 process」，兩者缺一不可，否則測試數據之間不具可比性，容易誤判根因。

## 3. 測試二：熱 Key 極限併發測試

### 3.1 測試設計

沿用相同的四階段負載曲線，但 Setup 階段僅建立 **1 組**熱點短網址，主體持續讓 200 VU 峰值全數併發鎖定同一組短碼（而非隨機挑選），模擬單一熱門連結在短時間內被大量集中點擊的極端情境，用來驗證快取層在極端熱點下有無競爭條件（race condition）、資料錯亂問題，並額外交叉核對 Redis 快取命中率與非同步寫入緩衝的資料完整性。測試環境：全新純淨環境（清空 `short_urls` / `access_logs`、FlushDB Redis、重啟 JVM process）。

### 3.2 測試結果

| 指標 | 門檻標準 | 實測結果 | 判定 |
|---|---|---|---|
| P95 延遲 | < 200ms | **46.45 ms** | ✅ PASS |
| P99 延遲 | < 500ms | **70.33 ms** | ✅ PASS |
| 錯誤率 | < 1% | **0.00%** | ✅ PASS |
| 轉址正確率（Location Header 比對） | = 100% | **100.00%**（1,922,382 / 1,922,382） | ✅ PASS |
| 吞吐量 | — | **8,006.05 req/s** | 參考值 |

4 分鐘內累積 **192 萬次**請求，全數集中鎖定單一短碼，302 與 Location Header 比對全數正確，無任何跳轉錯誤或資料錯亂。

### 3.3 Redis 快取命中率驗證

| 項目 | 增量 | 命中率 |
|---|---|---|
| Keyspace Hits | +5,500,000+ | **100.00%** |
| Keyspace Misses | +0（測試期間） | — |


當 200 個使用者每秒瘋狂點擊同一條熱門短網址時，**100% 的請求全都在 Redis（記憶體快取）直接拿到結果並秒回跳轉**，完全沒有任何一次請求跑去打擾 MySQL 資料庫。這代表快取成功扛下了所有的瞬間暴量，資料庫非常安全、完全不會被塞爆。

### 3.4 點擊次數「對帳」：每秒 8,000 次點擊會不會漏算？

系統採用非同步設計：點擊先暫存於 Redis 記憶體，再由背景排程每 5 秒批次回寫 MySQL。我們直接比對最終數據：

- **k6 壓測端發送成功的轉址總次數**：**1,922,382 次**
- **MySQL 資料庫最終累計的 `click_count`**：**1,922,382 次**

**結論**：
在每秒超過 8,000 次的極限高壓下，**點擊次數「1 筆都沒漏掉」（準確率 100.00%，0 遺失）**！而且因為數據是先在記憶體暫存、由背景非同步寫入資料庫，所以完全不會拖慢使用者的轉址速度。

### 3.5 小結

這份熱 Key 測試證明了兩件最重要的事：
1. **快取超給力**：再熱門的連結，流量全被 Redis 擋在門外，資料庫完全零負擔。
2. **記帳超精準**：流量再大、點擊再快，背後的點擊統計依舊 100% 精準，沒有漏算任何一次點擊。

## 4. 測試方法論決策：本階段不執行「最大負荷測試」

### 4.1 決策原因

規劃階段曾考慮加入「持續加壓直到系統出現錯誤或延遲爆掉」的最大負荷測試，用以找出系統的絕對 QPS 上限。**經評估後決定本階段不執行**，原因如下：

- 目前測試環境是單一筆電，同時運行 Spring Boot、MySQL、Redis 與 k6（壓測端），四者互搶 CPU/記憶體資源
- 在此條件下測出的「上限」，反映的可能是**筆電硬體資源被榨乾**，而非系統程式邏輯或架構設計的真實承載能力，兩者無法區分,數據可信度不足
- 真正有意義的最大負荷測試，需要將壓測端與被測系統部署在**物理隔離**的機器上，並搭配伺服器端資源監控（CPU/記憶體/連線池即時狀況），才能確保測出的極限值真實反映系統本身的設計承載量

此決策本身也是本階段測試方法論上的一個重要產出：**釐清了「測試數據在什麼條件下才具有意義」，避免產出誤導性的結論。**

### 4.2 後續若要執行的前提條件

- 壓測端（k6）與被測系統（App + DB + Cache）部署在不同機器
- 被測系統端具備基本監控（CPU、記憶體、連線池使用率）
- 明確的驗證目標（例如：驗證系統是否能撐住預期的生產流量峰值），而非漫無目的地持續加壓

## 5. 本階段結論

1. **正確性通過驗證**：累計超過 700 萬次請求（五輪全域隨機對照測試 + 熱key測試），302 跳轉與 Location Header 正確率始終維持 100%，未出現任何資料錯亂或跳轉錯誤，系統的核心轉址邏輯在高併發下具備良好的正確性保證。
2. **效能達標**：在乾淨環境、200 VU 併發下，全域隨機讀取 P95 = 45.39ms／P99 = 67.86ms、熱key極限情境 P95 = 46.45ms／P99 = 70.33ms，兩種情境延遲表現幾乎一致，均遠低於預設門檻（200ms / 500ms）。
3. **快取層防護與資料完整性通過驗證**：熱key測試證實 Redis 在極端集中流量下維持 100% 命中率、0 穿透，且非同步寫入緩衝機制在 8,000+ req/s 高頻打點下達成 0 筆遺失，快取防護設計與非同步架構均禁得起實測。
4. **測試方法論的收穫,與原始效能數字同等重要**：
   - 確認了「測試環境初始狀態一致性」對壓測數據可信度的重大影響，並建立了標準化的環境重置流程（清空 DB/Cache + 重啟 process）
   - 透過控制變因法，正確排除了「日誌等級」這個誤導性假設，避免得出錯誤結論
   - 清楚界定了「最大負荷測試」在目前環境下不具備執行意義的原因，避免產出不可信的數據
